What I stopped doing by hand: four automations that gave my team its time back

I lead a small development team. Over the years we have built more than a hundred web platforms: project websites, e-learning platforms, internal tools. If you build at that pace, you notice something early on. A surprising share of the week is spent on tasks that are not hard, just repetitive.

Creating a new site. Setting up an account for a new colleague. Copying files to a server and hoping nothing breaks. None of it needs creativity, but all of it needs attention, because a small slip costs hours later.

This year I decided to stop doing those tasks by hand. I used AI as a working partner to design, build and test the automations, and I kept the rule that a person stays in charge of every decision that matters. Here is what changed, and how you could do the same in your team or company.

The numbers first

TaskBeforeNow

These are not lab numbers. They are the everyday tasks my team and I did every week.

1. New site setup: from a 2-hour checklist to one command

The pain. Every new platform started from our base template. Someone had to create the hosting account, copy the template, create the database, connect it, set new passwords, and then work through a long settings checklist. It took about two hours. And since people do things slightly differently, no two sites were set up exactly alike.

What runs now. One script creates the hosting space (or a subdomain), clones the base template on the server, creates the database, sets fresh passwords and removes what should not go live. The developer then opens a single "site setup" screen inside the platform, fills in the project details and applies the standard settings in one go. Our existing quality check still runs at the end, as before. It just finds much less.

How you can start. You probably already have a setup document or checklist. That is your specification. Go through it line by line and mark each step "same every time" or "needs judgment". Automate the first group only. The judgment steps stay with people, and that is fine.

2. On/offboarding: 5 minutes, and nothing forgotten

The pain. A new colleague needs an email account, calendar access, the right groups, a project-management account with the correct team and working hours, and a welcome email. A leaver needs the opposite, and the order matters: lock the account, archive the mailbox, hand files to the manager, reassign open tasks, remove access everywhere. Doing this by hand took close to an hour, and the risk was not the time. It was the one step someone forgets.

What runs now. I type one request in plain words, for example the person's name, role, team and personal email. The automation checks everything first and shows me a full preview of what it is about to do. Only after I confirm does it make the changes across all systems. For leavers it secures the account, starts the archive and the file transfer, and reassigns tasks. Whatever still has to be done by hand is listed at the end, so nothing falls through the cracks.

How you can start. Most tools you already use (email, calendar, project management) have an API. Start with onboarding, because it is lower risk: creating things is easier to undo than removing them. Once it works, build offboarding on the same base.

3. Auto-deploy: merge and walk away

The pain. Deploying an update meant packing files, uploading them to the server, replacing the old version and clicking around to see if the site still worked. About thirty minutes each time, with no real checks, and some nervousness every time.

What runs now. When a change is merged into the main branch, the pipeline packs only the files that belong on the server and sends them there. On the server, one fixed script takes over. It checks the package, backs up the current version, puts the new one in place and tests that the site still answers correctly. If it does not, the script restores the backup by itself and the person who merged gets a notification. A failed deploy never leaves the site broken.

The deploy access is locked down to that one job and nothing else.

How you can start. Most code hosting platforms include a pipeline feature. Begin with the boring version: deploy on merge, keep a backup, test one page. Add the automatic rollback next. That is the part that lets you stop worrying.

4. Automatic checks before merge

The pain. Code review used to cover everything, from real logic problems to formatting, typos and accidentally committed passwords. Reviewers spent their attention on things a machine can spot.

What runs now. Every pull request runs automatic checks before review: a scan for leaked secrets and keys, coding-standard checks and static analysis that catch bugs and security issues before a person reads the code. The deploy adds a syntax check of its own. People review what people are good at: design, logic, and "is this the right solution?".

How you can start. Add a secret scanner first. It is quick to set up and protects you from the most expensive mistake. Then add a linter and a static analyser for your main language. If your old code has many warnings, start with a baseline so only new problems block a merge.

What I learned

Preview before action. Every automation that changes something shows me exactly what it will do and waits for a "yes". This one rule is what made me comfortable letting automations touch real accounts and live servers.

Never guess. If a team name does not exist, or a name matches two people, the automation stops and lists the options. A wrong guess done automatically is worse than a slow manual step.

AI is a strong partner, not the boss. I used AI to write designs, code and tests, and to review its own work. It was faster than doing it all myself, by a lot. But every decision about what should happen, what should stay manual, and what is risky stayed with me.

Automate the boring 80%, leave the rest. Each of these automations still has a few manual steps on purpose. Chasing 100% often costs more than it saves.

Write it down as you go. Each automation has a short document that says what it does, what is still manual and where to pick up next time. Six months from now, that is what will save you, or the colleague who takes it over.

Where to start in your team

Pick the task your team complains about most that is also the same every time. Write the steps down, mark which ones need judgment, and automate the rest with a preview and a confirmation in front of it. Measure the time before and after.

Then do the next one.
